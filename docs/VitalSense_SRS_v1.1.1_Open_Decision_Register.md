# VitalSense SRS v1.1.1 — Decision Register

**Governance Status:** Ten core architecture and product decisions (`OD-01`, `OD-03`, `OD-04`, `OD-07`, `OD-14`, `OD-16`, `OD-17`, `OD-18`, `OD-19`, `OD-22`) were formally **APPROVED by the Product Owner** during Milestone 0.5.3 and finalized in Milestone 0.6. The remaining 12 decisions remain explicitly **OPEN** and will be resolved at their designated phase gates.

---

## 1. Approved Product-Owner Decisions (Milestones 0.5.3 / 0.6)

| Decision ID & Title | Status | Approved Decision & Terms | Affected Specs | Resolution Gate & Milestone |
|---|---|---|---|---|
| **OD-01** — Phase 1 Metric Categories & Source Integrations | **APPROVED (Option B)** | Includes 10 core metrics: `steps`, `heart_rate`, `sleep_session`, `active_energy`, `workout_session`, `resting_heart_rate`, `blood_pressure_systolic`, `blood_pressure_diastolic`, `blood_oxygen_saturation` (SpO2), `blood_glucose`. Blood pressure requires paired systolic/diastolic measurements. Honest empty-state enforcement (no fabricated zeros). Weight/body measurements preserved as separately tracked scope item. | FR-DATA-001–013; FR-METRIC-001–005; IF-HEALTH-*; Appendix C | Resolved in Milestone 0.6; guides Milestone 0.7 Migration 002. |
| **OD-03** — Phase 0 Exit Acceptance Criteria | **APPROVED (Assistant Delegation)** | Objective 4-pillar verifiable acceptance criteria: 1) Foundation readiness (100% test pass, reversible migrations, zero OpenAPI drift, health/readiness probes HTTP 200), 2) Data pipeline readiness (synthetic batch ingestion, numeric precision), 3) Cross-platform application readiness, 4) End-to-end release readiness. Checklists alone do not claim readiness; independent execution evidence required. | DEP-*; ARCH-*; NFR-*; SYNC-*; Section 16 | Phase 0 Gate accepted in Milestone 0.6. |
| **OD-04** — Manual Entry and Correction Behavior | **APPROVED (Option A)** | Controlled manual entry restricted to approved Phase 1 metrics (`origin='user_entered'`). Immutable revision lineage: edits mark prior record `superseded` and insert new record with `correction_state='corrected'` referencing `superseded_by_id`. Corrections preserve original measurement timestamp. Deletions generate tombstones. | FR-MAN-001–005; FR-METRIC-*; FR-QUAL-006; SYNC-017/018; Appendix C | Resolved in Milestone 0.6; schema migration in Milestone 0.7. |
| **OD-07** — Data Retention, Export, Deletion, and Backups | **APPROVED (Option A with Safeguards)** | 30-day rolling raw ingestion payload retention (`raw_payload = NULL` after 30 days while preserving receipt metadata). Normalized records retained while account is active. 14-day server log retention with 100% PHI redaction. 30-day account deletion grace period. 30-day rolling backup snapshot expiry. Backup restoration reconciles against `audit_events` deletion records. Deletion covers personal records, derived analytics, predictions, caches, and reports. Configurable retention; no automatic HIPAA/GDPR claims. | FR-PRIV-004–007; PRV-003/005–007; DATA-009; SYNC-009/019; PRV-012–016; Appendix D | Resolved in Milestone 0.6; lifecycle worker in Milestone 0.7. |
| **OD-14** — Deletion Propagation, Tombstones, & Offline Sync | **APPROVED (Option A with Safeguards)** | Dedicated `sync_tombstones` table. Per-device synchronization cursors (`last_sync_timestamp`). On expired cursor (>30 days), server returns `SYNC_CURSOR_EXPIRED`. Client executes safe full resync: **never blindly wipe local database**; preserve pending uncommitted offline edits and drafts, reconcile with server before replacing cache. Account deletion overrides pending offline uploads. PostgreSQL remains canonical server source. | FR-PRIV-004; PRV-005–007; PRV-012; SYNC-019; Appendix D | Resolved in Milestone 0.6; sync endpoint in Milestone 0.7. |
| **OD-16** — Platform Support Matrix | **APPROVED (Option A Expanded)** | All five platforms are first-class targets planned and developed in parallel: 1) Android, 2) iOS, 3) Windows, 4) macOS, 5) Web. Independent client apps and release pipelines. Shared identity, canonical health records, shared API contracts, and sync rules. Android evaluates Health Connect; iOS/macOS evaluate HealthKit. Desktop primarily consumes synchronized data (no invented phone sensors). Validated minimum versions: iOS 16+, Android 12+ (Health Connect), Windows 10/11, macOS 13+ (Ventura), evergreen browsers. | NFR-COMP-001–003; FR-DATA-001/002; IF-CLIENT-*; Appendix C/F | Resolved in Milestone 0.6; governs client workspace setup. |
| **OD-17** — Local Database Encryption & Key Management | **APPROVED (Option A)** | Equivalent local-data protection across all five platforms: encrypted local health-data storage. SQLCipher AES-256 where SQLite is used. Cryptographically secure random keys in hardware-backed storage (Android KeyStore, iOS/macOS Keychain, Windows DPAPI). Room evaluated as Android-specific abstraction behind common repository contracts. Web uses IndexedDB with Web Crypto (noted as browser-appropriate, distinct from hardware-backed storage). Key-loss recovery via server resync. Secure logout evicts keys and unlinks local database. | SEC-008; SYNC-001–013; ARCH-005; FR-PRIV-004; PRV-014 | Resolved in Milestone 0.6; governs client local DB architecture. |
| **OD-18** — Authentication Strategy and Session Lifecycle | **APPROVED (Option A)** | Self-hosted identity system in PostgreSQL. Argon2id password hashing. OAuth2 PKCE for planned Apple and Google sign-in. 15-minute stateless JWT access tokens. 7-day rotating refresh tokens stored hashed in `auth_refresh_tokens`. Refresh token reuse detection triggers immediate token-family revocation. Web uses HttpOnly, Secure, SameSite cookies with CSRF tokens. Native clients use secure platform storage. Rate limiting, brute-force protection, audit events, session revocation across devices. | FR-AUTH-001–008; SEC-001–011; IF-API-014 | Resolved in Milestone 0.6; auth endpoints in Milestone 0.7. |
| **OD-19** — Hosting Topology and Service Boundary | **APPROVED (Option A)** | Centrally deployed backend initially as a Modular Monolith. Strict logical Web (`/api/v1/web`) and Mobile/Client (`/api/v1/mobile`) routing namespaces. Shared identity and canonical health data. Independently runnable background workers from same codebase container. Stateless design supporting multi-instance horizontal scaling for concurrent users/devices. Mobile-first responsive frontend across phones, tablets, laptops, desktops. PostgreSQL is canonical store. Future modular extraction preserved. | ARCH-001–015; DEP-*; NFR-REL-*; Section 11; Appendix E.5 | Resolved in Milestone 0.6; governs deployment architecture. |
| **OD-22** — Automation Boundary: Backend Workers vs. n8n | **APPROVED (Option A)** | n8n is strictly an external workflow orchestrator (cron schedules, non-sensitive notifications, triggering backend operations via authenticated webhooks). VitalSense backend retains 100% ownership of auth, authorization, sensitive health data, validation, canonical DB writes, sync, and ML. Zero direct n8n PostgreSQL connections; zero identifiable health measurements sent to n8n. Webhooks use least-privilege tokens, idempotency, and audit logging. | FR-AUTO-001–013; IF-AUTO-001–005; ARCH-008/015; DEP-*; Appendix E.4 | Resolved in Milestone 0.6; governs automation interface design. |
